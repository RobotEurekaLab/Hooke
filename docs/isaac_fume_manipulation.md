## 改动及原因

1. **共享窗扇资产加入理想配重等效模型。** 对窗扇和把手取消重力净载荷，保留质量、惯量、滑轨阻尼和摩擦。没有窗扇位置伺服，也没有在操作过程中直接设置窗扇位姿或施加关窗力。此为理想平衡近似，未模拟真实配重绳轮。
2. **修正把手轴向和接近方向。** 把手沿仪器局部 X 轴横置，机器人沿前面法线接近；原来的基座到把手连线会切过侧墙。两个后端使用相同修改后的源 MJCF。
3. **增加固定准备位姿及双指抓取检查。** 先到柜前可达区域再接近，避免初始扰动触发碰撞的肘部解；左右指垫均接触把手后才继续下拉，否则明确报错。

验收仍使用 `hooke-manipulation-v2`：终态误差 <20 mm、把手接触 ≥50 ms、接触期间沿关闭方向净位移 ≥50 mm。原 `task.check()` 和 15 秒时限均未放宽。

## 对照与真实渲染

原 `cfdb499` 基线中，两边各 10/10 回合虽能结束，但严格操作判据都是 0/10。只加入配重时，MuJoCo seed 0 仍完全抓不到把手；修正接近方向后最初为 9/10，seed 1 的上臂碰柜导致失败。准备位姿修复后重新运行整个固定种子集合。失败原始记录保留，未覆盖。

禁止夹爪闭合的 MuJoCo seed 0 对照，在抓取检查处按预期报错，窗仍开启。孤立资产测试中，中间开度 90 mm 保持 15 秒不漂移；施加正负 5 N、0.2 秒的测试载荷均能推动窗扇，排除“冻结或锁死”造成保持。取消配重的单元对照则重新在重力下下落。

两个后端另各运行一个完整 seed 0 渲染回合，外部与腕部相机均输出真实图像；与多种子无渲染统计分开记录。

## 复现

在 `Hooke/` 源码目录执行，Python 环境需含项目依赖并配置 Isaac 安装位置：

```bash
python -m backends.matrix --task close_fume_hood \
  --mode expert --mode no_action --control-seconds 15 \
  --output ../temp/backend_parity/fume_recheck
```

渲染可分别运行 `python -m backends.run --task close_fume_hood --backend mujoco --output <新目录>` 与 `--backend isaac`。本机 MuJoCo EGL 使用物理 GPU 6，Isaac 默认 GPU 6；原生进程串行运行。

[逐回合结果、源快照比较和诊断指标](validation/isaac_fume_manipulation_summary.json)。原始日志、快照、轨迹、图像和视频位于忽略的 `temp/backend_parity/`，不随分支上传。
